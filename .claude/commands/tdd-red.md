# /tdd-red — 실패하는 테스트 하나 작성

Kent Beck TDD의 **Red** 단계다. `CLAUDE.md`의 "개발 프로세스" 절을 따른다. 대상 항목은 `TDD-IMPLEMENTS.md`에서 고른다.

인자: `$ARGUMENTS`

## 1. 항목 고르기

1. `TDD-IMPLEMENTS.md`를 읽는다.
2. 상태가 `RED` 또는 `GREEN`인 항목이 있으면 **멈춘다.** 그 항목 ID와 다음에 실행할 명령어(`RED`면 `/tdd-green`, `GREEN`이면 `/tdd-refactor`)를 알려준다. 한 번에 한 항목만 진행한다.
3. 인자로 ID를 받았으면 그 항목을 고른다. 그 항목이 `TODO`가 아니거나 앞에 `TODO` 항목이 남아 있으면, 이유를 말하고 사용자에게 확인을 받는다.
4. 인자가 없으면 위에서부터 첫 번째 `TODO` 항목을 고른다.
5. 모든 항목이 `DONE`이면 그렇다고 알리고 끝낸다.

## 2. 준비 조건 확인

- `package.json`이 없으면 `T00` 항목의 내용대로 먼저 만든다. 이것은 구조적 준비이며, 테스트 코드나 제품 코드를 넣지 않는다.
- 테스트 픽스처에 필요한 의존성(예: 워크북을 만드는 `xlsx`)이 아직 설치되지 않았으면 항목에 적힌 대로 설치한다. 제품 코드용 의존성은 설치하지 않는다.

## 3. 테스트 작성

- 항목에 적힌 **테스트 파일**에 **테스트 이름** 그대로 테스트 **하나만** 추가한다.
- 러너는 `node:test`, 단언은 `node:assert/strict`를 쓴다.
- 항목의 "주어진 상황 → 기대 결과"를 그대로 단언으로 옮긴다. 기대 결과를 넓히거나 다른 경우를 함께 검사하지 않는다.
- **제품 코드(`src/`, `public/`, `server.mjs`)는 만들지도 고치지도 않는다.** 빈 파일, 빈 함수, 스텁도 만들지 않는다.
- 기존 테스트를 고치지 않는다.

## 4. 실패 확인

1. 새 테스트만 실행한다: `node --test --test-name-pattern="<테스트 이름>" <테스트 파일>`
2. 실패해야 한다. 실패 이유가 항목의 "Red 기대 실패"와 맞는지 확인한다.
   - 맞으면 다음 단계로 간다.
   - 테스트가 **통과하면** 이미 구현된 행위다. 테스트를 지우지 말고 멈춘 뒤 사용자에게 알린다.
   - 오타, 문법 오류, 잘못된 import 경로처럼 **테스트 자체의 결함**으로 실패하면 테스트를 고치고 다시 실행한다.
3. 전체 테스트를 실행한다: `npm test`. 새 테스트 하나를 빼고 나머지는 모두 통과해야 한다.

## 5. 기록

`TDD-IMPLEMENTS.md`에서 이 항목을 갱신한다.

- `상태`를 `TODO`에서 `RED`로 바꾼다.
- `Red 기록`에 실패 메시지의 핵심 한 줄을 적는다.

**커밋하지 않는다.** 테스트가 실패하는 상태이기 때문이다(커밋 규율 1번).

## 6. 보고

다음 세 줄만 보고한다.

- 항목 ID와 테스트 이름
- 실패 메시지 핵심 한 줄
- 다음 단계: `/tdd-green`
