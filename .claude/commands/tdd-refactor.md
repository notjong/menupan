# /tdd-refactor — 구조 개선 (Tidy First)

Kent Beck TDD의 **Refactor** 단계다. `CLAUDE.md`의 "Tidy First 접근법"과 "리팩터링 가이드라인"을 따른다. 이 단계는 **구조적 변경만** 한다. 행위를 바꾸지 않는다.

## 1. 항목 확인

1. `TDD-IMPLEMENTS.md`를 읽는다.
2. 상태가 `GREEN`인 항목을 찾는다. 없으면 멈추고, 현재 상태에 맞는 명령어(`/tdd-red` 또는 `/tdd-green`)를 알린다.
3. `npm test`를 실행한다. 모두 통과해야 시작한다. 실패하면 멈추고 사용자에게 알린다.

## 2. 점검

이 항목이 건드린 파일과 그 테스트 파일을 읽고 아래 순서로 점검한다. `Green 기록`에 적힌 하드코딩부터 본다.

1. **하드코딩**: 테스트의 기대값을 그대로 반환하는 상수(Fake It). 이미 쌓인 테스트로 일반화할 수 있으면 일반화한다. 아직 테스트가 하나뿐이라 일반화의 근거가 없으면 남겨 두고, 그 사실을 기록한다(다음 테스트가 삼각측량한다).
2. **중복**: 테스트와 코드 사이, 코드 안, 테스트 안의 중복.
3. **매직 넘버·문자열**: 의미를 이름으로 드러낼 값(예: `300`, `"_"`, `"Y"`).
4. **이름**: 함수·변수·파일 이름이 의도를 드러내는가.
5. **단일 책임**: 함수가 한 가지 일만 하는가. 순수 로직과 I/O가 섞였는가.
6. **의존성**: 숨은 의존성(전역 시계, 고정 경로, 전역 상태)을 인자로 드러낼 수 있는가.
7. **문서 규칙**: `docs/TRD.md`의 데이터 계약, `.claude/rules/anti-ai-slop.md`(UI 코드일 때)와 맞는가.

점검 결과 고칠 것이 없으면 "변경 없음"으로 기록하고 5단계로 간다. 억지로 고치지 않는다.

## 3. 리팩터링

- 한 번에 **하나의** 리팩터링만 한다. 정립된 이름을 쓴다(예: Extract Function, Rename Variable, Introduce Constant, Inline Variable, Move Function, Introduce Parameter).
- 리팩터링 하나를 끝낼 때마다 `npm test`를 실행한다. 실패하면 그 리팩터링을 되돌리고 다른 방법을 찾는다.
- **하지 않는 것**
  - 새 기능, 새 분기, 새 예외 처리 추가 (행위적 변경이다. 다음 `/tdd-red` 항목이 할 일이다)
  - 테스트의 기대값이나 검사 범위 변경 (테스트 코드의 중복 제거와 이름 정리는 된다)
  - 이번 항목과 관계없는 파일 정리

## 4. 확인

1. `npm test` 전체 통과.
2. 경고 없음.
3. `git diff`로 행위 변경이 섞이지 않았는지 다시 본다.

## 5. 기록

`TDD-IMPLEMENTS.md`에서 이 항목을 갱신한다.

- `상태`를 `GREEN`에서 `DONE`으로 바꾼다.
- `Refactor 기록`에 적용한 리팩터링 이름 목록을 적는다. 없으면 "변경 없음"과 이유를 적는다. 남겨 둔 하드코딩이 있으면 어느 항목에서 풀릴지 적는다.

`plan.md`에서 같은 테스트 이름의 `- [ ]`를 `- [x]`로 바꾼다.

## 6. 커밋 (구조적 변경)

- 리팩터링을 했으면 커밋한다.

```text
refactor(<모듈>): <적용한 리팩터링 요약>

[STRUCTURAL] <항목 ID> <리팩터링 이름 목록>
```

- 리팩터링이 없었으면 기록 변경만 커밋한다.

```text
chore(tdd): <항목 ID> 완료 표시

[STRUCTURAL] 변경 없음
```

## 7. 보고

다음 세 줄만 보고한다.

- 항목 ID와 적용한 리팩터링(또는 "변경 없음")
- 남은 하드코딩과 그것을 풀 항목
- 다음 단계: `/tdd-red` (다음 항목 ID)
